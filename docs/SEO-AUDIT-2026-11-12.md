**Scope:** the public web surface of `apps/client` (Expo Router + React Native Web): `/`, `/welcome`, `/login`, `/register`, and the SPA shell served by `apps/client/nginx.conf`.
**Method:** production build (`npx expo export --platform web`), served with an nginx-equivalent SPA fallback, inspected with Lighthouse and the rendered DOM. Report-only — no application code changed.

## Verdict

**The web app is effectively invisible to search engines and social platforms today.** The shipped bundle is a client-rendered SPA: the HTML that a crawler receives contains an empty `<div id="root">`, one generic `<title>`, and no description, canonical, Open Graph, or structured data. Every route serves the same 1.6 kB shell, `robots.txt` is answered with HTML, and unknown URLs return `200`. There is no sitemap.

This is not a tuning problem — it is a rendering-mode and head-metadata problem. The good news is that the fix is well-trodden for expo-router: switch to static export, add `+html.tsx`, per-route `<Head>`, `public/robots.txt`, and a real 404.

## Findings

### P0 — Blocks indexing / sharing

#### P0-1. Client-only rendering: crawlers get an empty document

`apps/client/app.json`:

```json
"web": { "bundler": "metro", "output": "single", "favicon": "./assets/images/favicon.png" }
```

Exported HTML (verbatim, 1 621 bytes):

```html
<div id="root"></div>
<script src="/_expo/static/js/web/entry-….js" defer></script>
```

Rendered DOM after JS: 409 characters of text on `/welcome`, 0 on first paint. Googlebot can render JS, but it is deferred and budgeted; Bing, LinkedIn, Facebook, X, Slack, WhatsApp, Discord and most LLM crawlers **do not**. Result: no rich previews, weak/no indexing, and no per-page snippet.

**Fix:** set `"output": "static"` (Expo Router SSG) and export per-route HTML, or `"server"` if dynamic rendering is preferred. Static is enough here — the public routes are deterministic. Verify the build still passes (the app reads `localStorage` only inside effects, but do confirm).

#### P0-2. `robots.txt` is invalid in production

`apps/client/nginx.conf:61-64`:

```nginx
location / {
    try_files $uri $uri/ /index.html;
}
```

There is no `public/robots.txt`, so `/robots.txt` falls through to `index.html`. Verified against the built bundle with an identical fallback:

```
/robots.txt   200  text/html  len=1621
/sitemap.xml  200  text/html  len=1621
```

Lighthouse: **`robots-txt` — "35 errors found"** — it parses HTML as a robots file. Search engines may treat the site as having no usable crawl directives, and some will clamp crawl rate.

**Fix:** add `apps/client/public/robots.txt` (Expo copies `public/` verbatim) and make nginx serve it as a file:

```txt
User-agent: *
Allow: /welcome
Allow: /login
Allow: /register
Disallow: /dashboard
Disallow: /finances
Disallow: /wishes
Disallow: /doos
Disallow: /settings
Disallow: /api/
Sitemap: https://<your-domain>/sitemap.xml
```

Also add `location = /robots.txt { default_type text/plain; }` (or rely on the file, which nginx types correctly by extension).

#### P0-3. No per-page metadata: one title, no description, no canonical, no social cards

Exported `<head>` contains only charset, X-UA-Compatible, viewport, title, reset styles, the Google Fonts stylesheet, the CSS bundle, and the favicon.

Measured on both `/welcome` and `/login`:

```
title:        Wishes & DOOs
meta desc:    null
canonical:    null
og:*:         0
twitter:*:    0
json-ld:      0
robots meta:  null
```

`expo-router/head` is not used anywhere (grep: zero matches). So titles never change on navigation, and every URL is a duplicate of every other URL as far as a crawler is concerned.

**Fix:**
- Add `apps/client/app/+html.tsx` with the static shell: `lang="en"`, description, canonical, OG/Twitter defaults, `theme-color`, apple-touch-icon, `preconnect` to the font host, and JSON-LD (`WebApplication` / `Organization`).
- Add per-route `<Head>` from `expo-router/head` in `welcome.tsx`, `login.tsx`, `register.tsx` with unique titles/descriptions/canonicals. Example:

```tsx
import Head from "expo-router/head";

<Head>
  <title>Wishes &amp; DOOs — fund your wishes, finish your DOOs</title>
  <meta name="description" content="A calm personal finance and wishlist app: connect accounts, budgets, savings goals, wishes and daily tasks in one workspace." />
  <link rel="canonical" href="https://<your-domain>/welcome" />
  <meta property="og:title" content="Wishes &amp; DOOs" />
  <meta property="og:description" content="Fund your wishes. Finish your DOOs." />
  <meta property="og:image" content="https://<your-domain>/og/wishesanddoos.png" />
  <meta property="og:type" content="website" />
  <meta name="twitter:card" content="summary_large_image" />
</Head>
```

Title `Wishes & DOOs` is 13 characters, brand-only. Aim for 50–60 characters with the value proposition; descriptions 140–160.

#### P0-4. `/` is a client-side redirect to `/welcome`

`apps/client/app/index.tsx:4-6` renders `<Redirect href="/welcome" />`. The server returns the same 200 shell for both URLs; the redirect only happens after JS runs. That leaves:

- two indexable URLs with identical content,
- a root URL that renders blank,
- no server-side 301 to consolidate signals.

**Fix:** either make `/welcome` the landing route (move the screen to `app/index.tsx` and keep a permanent redirect for `/welcome`), or add `location = / { return 301 /welcome; }` in nginx and a canonical on `/welcome`.

#### P0-5. Zero heading structure

`accessibilityRole="header"` / `role="heading"` appears nowhere in `app/**` or `src/**`. React Native Web renders `<Text>` as `<div>`, so the hero copy — the only real `<h1>` candidate — is an unheaded `div`. Verified: `document.querySelectorAll('h1,h2,h3,h4,h5,h6').length === 0` on `/welcome` and `/login`.

Beyond classic SEO (headings are a relevance signal), this hurts screen-reader navigation and text extraction.

**Fix:** mark the hero title as a heading:

```tsx
<Text accessibilityRole="header" aria-level={1} style={...}>
```

and use level 2 for section titles (`Finances`, `Wishes`, `DOOs`). Keep the visual sizes — semantics and styling are independent.

#### P0-6. Soft 404: every unknown URL returns `200`

```
/this-page-does-not-exist   200  text/html  len=1621
```

There is no `app/+not-found.tsx`, and nginx falls back to `index.html` for anything that does not exist. Crawlers report these as "soft 404s" and may index the shell under arbitrary URLs.

**Fix:** add `app/+not-found.tsx`, export it as static HTML, and replace the fallback:

```nginx
location / {
    try_files $uri $uri.html $uri/index.html $uri/ =404;
}
error_page 404 /404.html;
```

(With `output: "static"`, `expo export` emits route HTML you can match with `try_files`.)

### P1 — Limits reach and quality

#### P1-1. No sitemap
No `public/sitemap.xml`; the URL is answered with HTML. With four public routes it is small, but it is how you declare `/welcome`, `/login`, `/register` and any future content. Add it and reference it from `robots.txt`.

#### P1-2. Images have no `alt` text
`app/(app)/wishes.tsx:307` and `app/(app)/wishes/[id].tsx` (image preview) render `<Image source={{ uri: wish.image_url }} />` with no `alt` / `accessibilityLabel`. On web this becomes an `<img>` with no `alt`. Lighthouse scores `image-alt` as n/a on the public page only because there are no images there.

**Fix:** `alt={wish.title ? `Photo for ${wish.title}` : "Wish photo"}`; decorative images get `alt=""`.

#### P1-3. The Spanish translation is invisible to search
`src/i18n/LanguageProvider.tsx` defines `AppLanguage = "en" | "es"` and persists the choice in `localStorage` (`:587-609`). There are no locale-prefixed routes (`/es/...`), no `hreflang`, and `<html lang>` is hard-coded `"en"` and never updated on switch.

Consequences: Spanish content is never crawled, and after switching languages the document still declares English (bad for screen readers and browser translation).

**Fix:** add `/es` route variants (or a `?lang=es` canonical strategy), emit `rel="alternate" hreflang="en" / "es" / "x-default"`, and set `document.documentElement.lang` in the provider's effect.

#### P1-4. Core Web Vitals risk: one 1.87 MB JS chunk and render-blocking third-party fonts

Export: `_expo/static/js/web/entry-….js` = **1.87 MB** (uncompressed), CSS 12.2 kB, one chunk, no route-level code splitting (a consequence of `output: "single"`). The head also loads Google Fonts with a blocking stylesheet and no `preconnect`/`preload`:

```html
<link rel="stylesheet" href="https://fonts.googleapis.com/css2?family=Plus+Jakarta+Sans…&family=JetBrains+Mono…&display=swap">
```

LCP cannot start until ~1.9 MB of JS parses and React paints the hero. On mobile this is seconds. Core Web Vitals are a ranking input, and the app's own mobile-first standard makes this the critical path.

**Fix:** static rendering + route splitting gets first paint to HTML; self-host the two font families (or at least add `<link rel="preconnect" href="https://fonts.gstatic.com" crossorigin>` and preload the two woff2 files); audit whether all 16 exported icon fonts are needed (only MaterialIcons is requested at runtime, but ~4 MB of TTFs ship in `dist/assets`).

#### P1-5. Title is brand-only and identical everywhere
`Wishes & DOOs` is set once by app.json. No route changes it. See P0-3.

#### P1-6. Missing mobile/PWA metadata
No `theme-color`, no `apple-touch-icon` (180×180), no `manifest.webmanifest`, no 192/512 icons. Only `favicon.ico` (14.5 kB from the configured PNG). These affect mobile SERP/bookmark presentation and installability, not core ranking.

#### P1-7. Authenticated app routes are crawlable
`/dashboard`, `/finances`, `/wishes`, `/doos`, `/settings` return the shell with 200 and no `noindex`. If discovered (e.g. from a shared URL), crawlers index empty shells and dilute the site. Add `noindex` via `<Head>` on the `(app)` layout and/or `Disallow` in `robots.txt` (P0-2).

#### P1-8. There is almost nothing to rank, and no trust pages
Public surface is `/welcome`, `/login`, `/register`. There is no About, Pricing/FAQ, Privacy, Terms, or help content. For a finance-adjacent product, trust pages are both an E-E-A-T signal and a conversion requirement. The landing copy itself is short (`Fund your wishes. Finish your DOOs.` + one paragraph + three demo cards); it is a product demo, not indexable content.

**Fix (product decision):** add at least `/privacy`, `/terms`, `/about`, and one or two genuinely useful pages (e.g. "how savings goals work", "wishlist + task planning"). Each gets its own title, description, canonical, and heading structure.

### P2 — Polish

#### P2-1. Icon-font glyphs leak into the text layer
Rendered `body.innerText` begins with private-use glyph characters (the MaterialIcons glyphs) before `Wishes & DOOs`. Decorative icons should be hidden from assistive tech and text extraction:

```tsx
<MaterialIcons name="auto-awesome" accessibilityElementsHidden importantForAccessibility="no-hide-descendants" />
```

(or `aria-hidden` on web). This also makes copy/paste and translation cleaner.

#### P2-2. `<noscript>` is a dead end
The exported HTML says only *"You need to enable JavaScript to run this app."* With static rendering, put the hero copy in the prerendered HTML so no-JS visitors and non-JS crawlers see something useful.

#### P2-3. No host normalization
`server_name _;` with no `www` → apex redirect and no trailing-slash policy. Pick one canonical host and 301 the other; keep route URLs slash-free.

#### P2-4. Accessibility findings that also affect SEO extraction
Lighthouse accessibility 88: `aria-required-attr` (ARIA roles missing required attributes — the checkbox/switch patterns in the demo cards) and `color-contrast` (muted text on glass surfaces). Contrast failures are a readability/quality signal; the ARIA ones are easy fixes in `Card`/`Pressable` usage.

#### P2-5. No Search Console / analytics verification
No `google-site-verification` meta, no analytics, no Bing verification. You cannot measure indexing, queries, or CWV field data without them.

#### P2-6. No social image
No `og:image` asset exists in `assets/` and no `/og/` directory in `public/`. Even after adding tags, shares stay text-only.

## What already works

- `<html lang="en">`, `<meta charset="utf-8">`, and a correct viewport (`width=device-width, initial-scale=1`; no `user-scalable=no`, no `maximum-scale<5`).
- A `<title>` exists, so the basic Lighthouse title audit passes.
- **Crawlable anchors pass** — expo-router renders real `<a href>` elements, and link text is descriptive. No JS-only `onClick` navigation on the public pages.
- `main` landmark present; touch targets pass; best-practices 100; no console errors on load.
- Static assets are content-hashed and served with `Cache-Control: immutable` for 1 year; HTML is `no-cache, no-store, must-revalidate` (`nginx.conf:31-49`). Gzip is enabled for HTML/JS/CSS/JSON/SVG.
- Mobile-first layout and safe-area handling are already in good shape; the rendering problem is orthogonal to the design.
